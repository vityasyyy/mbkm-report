\subsection{Metodologi Kolaborasi}

Tim Software Engineering GDP Labs menggunakan metodologi Agile/Scrum. Sprint berdurasi dua hingga empat minggu dengan aktivitas rutin: daily stand-up (15 menit), sprint planning, sprint review, dan retrospective. Setiap perubahan kode dikirim melalui pull request (PR) di GitHub dan direview oleh setidaknya satu rekan tim sebelum di-merge.

\subsection{Kegiatan}

\subsubsection{Daily Stand-up dan Sprint Planning}

Setiap pagi tim mengadakan daily stand-up untuk menyampaikan progress kemarin, rencana hari ini, dan hambatan yang dihadapi. Kegiatan ini membuat blocker teknis terlihat lebih awal, sehingga rekan tim bisa menawarkan bantuan. Pada sprint planning, saya berdiskusi dengan Product Manager dan tim QA untuk memprioritaskan backlog dan memperkirakan kompleksitas tugas.

\subsubsection{Code Review dan PR Workflow}

Setiap PR yang saya buat menyertakan deskripsi berisi konteks perubahan, daftar file yang dimodifikasi, dan hasil pengujian yang relevan. Saya aktif menerima dan memberikan review. GDP Labs juga memakai AI-powered PR review agent (pr-agent) yang memberikan masukan awal soal gaya kode dan potensi bug, tetapi keputusan akhir tetap dipegang reviewer manusia.

Beberapa review yang saya terima mengubah cara saya menulis kode. Misalnya, feedback untuk mengeksternalkan query SQL ke file \texttt{.sql}, menyatukan fungsi basis data, dan memastikan setiap tool menangani konfigurasi yang hilang secara eksplisit. Saya juga mendapat review yang menuntut test coverage penuh pada tool yang menyentuh API eksternal, yang kemudian menjadi kebiasaan saya.

\subsubsection{GitHub Projects dan Task Tracking}

Proyek dikelola melalui GitHub Projects dengan kolom To Do, In Progress, In Review, dan Done. Saya memperbarui status tugas secara rutin, menambahkan komentar pada issue terkait, dan menjelaskan alasan teknis setiap keputusan di thread diskusi.

\subsection{Refleksi}

Kolaborasi dalam tim Agile tidak hanya soal kemampuan teknis. Komunikasi yang transparan soal progress dan blocker, serta keberanian untuk bertanya ketika belum paham, lebih sering menjadi penentu kelancaran sprint daripada kemampuan individu. Code review adalah instrumen belajar yang paling efektif selama magang: banyak pola yang saya pakai sekarang, seperti sanitasi identifier dan penanganan timeout eksplisit, saya pelajari dari review rekan senior.

Pengalaman ini memperkuat keyakinan saya bahwa perangkat lunak berkualitas dibangun oleh tim, dan bahwa menerima kritik atas kode tidak sama dengan dikritik secara personal.
