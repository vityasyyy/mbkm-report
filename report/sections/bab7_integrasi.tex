\subsection{Landasan Teori}

Pengujian integrasi memverifikasi bahwa komponen yang sudah lolos pengujian unit dapat berinteraksi dengan benar ketika digabungkan. Pada Digital Employee, pengujian integrasi mencakup alur agen dari coordinator ke sub-agen, tool, MCP, hingga API eksternal. Pengujian sistem memastikan aplikasi berfungsi sebagai satu kesatuan di lingkungan yang menyerupai produksi, termasuk pipeline CI/CD dan deployment.

\subsection{Kegiatan}

\subsubsection{Playwright End-to-End Testing untuk Alur MoM}

Tim engineering GDP Labs memakai Playwright (TypeScript) untuk pengujian end-to-end antarmuka Digital Employee. Saya mengembangkan pengujian untuk alur kerja Minutes of Meeting (MoM) di aplikasi DE-PM (PR \#629): pengecekan integrasi Meemo, pengambilan daftar rapat, pencarian dokumen MoM di Google Drive, konversi dokumen ke HTML, dan pengiriman email kepada peserta. Pengujian ini memakai skenario yang disiapkan sebelumnya dan sepenuhnya otomatis, dari penyiapan data hingga validasi hasil akhir.

\subsubsection{Playwright End-to-End Testing untuk DE-PM-Datasaur}

Untuk DE-PM-Datasaur, saya melakukan scaffolding proyek Playwright beserta kerangka pendukungnya (PR \#745):

\begin{itemize}
    \item \texttt{globalSetup} dan \texttt{globalTeardown} untuk penyiapan dan pembersihan data pengujian secara otomatis.
    \item Page objects dan test fixtures untuk antarmuka Slack, termasuk \texttt{slack-page.ts} yang mengabstraksi interaksi dengan panel Slack.
    \item Data seed skenario (\texttt{seed.py} + \texttt{scenarios.json}) dan helper MCP untuk meniru respons backend pada skenario end-to-end.
    \item Satu spec utama \texttt{datasaur\_pm\_e2e.spec.ts} yang mengeksekusi skenario, seperti merangkum thread Slack dan email, lalu memverifikasi hasilnya melalui keyword yang diharapkan.
\end{itemize}

\subsubsection{Konsolidasi Integration Test DE-PM}

Di akhir masa magang, saya merefaktor kumpulan integration test DE-PM yang sebelumnya terpisah per proyek menjadi pola env-driven single-agent (PR \#903). Satu pola pengujian yang didorong oleh konfigurasi lingkungan kini digunakan untuk semua proyek, sehingga menambah skenario tidak berarti menambah boilerplate test baru.

\subsubsection{Deployment dan Validasi Pipeline CI/CD}

Selama magang saya terlibat langsung dalam alur deployment Digital Employee melalui pull request deploy yang memicu pipeline CI/CD, baik ke lingkungan dev maupun prod. Saya menangani beberapa kegagalan pipeline yang disebabkan inkonsistensi lingkungan, misalnya konfigurasi variabel yang tertinggal setelah migrasi GLConnectors, dan menyesuaikan nilai Helm (ConfigMap/Secret) agar sesuai dengan kedua lingkungan.

Validasi setelah deployment dilakukan dengan memicu job Kubernetes CronJob secara manual dan memeriksa log output serta status akhir eksekusi, untuk memastikan agen dapat menjalankan siklus penuh: menerima instruksi, mengorkestrasi sub-agen, memanggil tool, dan mengembalikan hasil.

\subsection{Refleksi}

Dari pengujian end-to-end saya belajar bahwa scaffolding yang baik (global setup, fixtures, data seeding) menentukan kecepatan penulisan skenario berikutnya. Saat saya pertama kali menulis spec MoM, sebagian besar waktu habis untuk menyiapkan data dan menunggu respons bot; setelah infrastruktur seed dan polling dibuat, menambah skenario menjadi pekerjaan yang cepat.

Penanganan kegagalan pipeline CI/CD membuat saya memahami pentingnya dokumentasi lingkungan: perbedaan nilai konfigurasi antara dev dan prod adalah penyebab kegagalan yang paling sering, dan sulit ditemukan tanpa menyamakan sumber kebenaran konfigurasi.
