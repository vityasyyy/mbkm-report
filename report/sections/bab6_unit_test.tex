\subsection{Landasan Teori}

Pengujian unit dilakukan pada unit terkecil (fungsi atau metode) secara terisolasi untuk memastikan perilaku sesuai ekspektasi. Praktik yang saya gunakan mencakup isolasi dependensi eksternal dengan mock, skenario positif dan negatif, serta analisis cakupan (coverage). Tim Digital Employee menetapkan threshold cakupan yang tinggi, sehingga setiap tool baru harus disertai pengujian yang menyeluruh.

\subsection{Kegiatan}

\subsubsection{Pengujian Unit untuk Modul DE-WR}

Pengujian pada modul \texttt{digital-employee-weekly-report} mencakup:

\begin{itemize}
    \item \textbf{Google Drive search tool}: paginasi server-side dengan cursor-based caching, percabangan \texttt{page\_size}, dan loop \texttt{page\_token}, hingga cakupan 100\%.
    \item \textbf{Google Docs pagination}: cakupan percabangan \texttt{page\_size}.
    \item \textbf{Compliance summary email} (\texttt{SendComplianceSummaryEmailTool}): beberapa penerima, auto-resolution, validasi filter, dan penerimaan ejaan \textit{quarterly}.
    \item \textbf{Deteksi laporan kosong}: penghitungan placeholder \texttt{(please insert here)} (tepat 7 berarti kosong), validasi loop pemrosesan batch, dan validasi respons spreadsheet append.
    \item \textbf{Issue processing agent}: hardened JSON parsing, SQL precedence, dan rescoring idempotency.
\end{itemize}

\subsubsection{Pengujian Unit dan Integrasi untuk Modul DE-WRI}

Untuk \texttt{FetchEmployeeIssuesTool} pada modul DE-WRI, saya menyusun 56 unit test dan 5 integration test dengan cakupan 100\% pada modul \texttt{fetch\_employee\_issues}:

\begin{itemize}
    \item \textbf{Unit test}: validasi model (\texttt{IssueEntry}, \texttt{EmployeeIssues}, \texttt{Config}, \texttt{Output}), fungsi basis data (perhitungan rentang tanggal, pembangunan query, pengelompokan hasil), pengujian keamanan (validasi nama tabel, pencegahan SQL injection), dan pengujian \texttt{db\_utils} (sanitasi identifier, eksekusi query/write).
    \item \textbf{Integration test}: konektivitas basis data sungguhan, eksekusi query terhadap \texttt{dummy\_weekly\_reports}, pengelompokan data dengan record nyata, dan eksekusi tool end-to-end.
\end{itemize}

Pengujian tambahan mencakup unit test dan integration test untuk \texttt{SendEmailTool}, pengujian manajemen jadwal CLI (create/delete/info dengan penegakan idempotency), serta pengujian agent dan connector handler.

\begin{lstlisting}[caption={Contoh pengujian keamanan pada DE-WRI}]
import pytest

from digital_employee_weekly_report_issue_reoccuring.connectors.tools.utils.db_utils import (
    validate_table_name,
)

def test_sql_injection_prevention():
    malicious_table = "weekly_reports; DROP TABLE users;--"
    with pytest.raises(ValueError, match="Invalid table name"):
        validate_table_name(
            malicious_table,
            allowed_tables=frozenset({"weekly_reports"}),
        )
\end{lstlisting}

\subsubsection{Coverage Analysis dan Threshold Enforcement}

Pengujian dijalankan dengan \texttt{pytest -n 4} untuk eksekusi paralel dan \texttt{pytest-cov} untuk melaporkan cakupan. Konfigurasi pada \texttt{pyproject.toml} mengecualikan \texttt{main.py}, file migrasi, dan file terkait Docker dari perhitungan cakupan:

\begin{lstlisting}[caption={Konfigurasi pytest-cov pada pyproject.toml}]
[tool.coverage.run]
omit = [
    "*/main.py",
    "*/migration/*",
    "*/Dockerfile*",
    "*/tests/*",
]
\end{lstlisting}

Laporan \texttt{htmlcov/} saya pantau secara rutin untuk menemukan area yang belum tercakup, lalu menambahkan kasus uji yang sesuai.

\subsubsection{Mocking untuk Agent Dependencies}

Sub-agen Digital Employee bergantung pada layanan eksternal (LLM runtime, Google API, CATAPA), sehingga pengujiannya membutuhkan mock yang cermat. Saya menggunakan fixture pytest berupa mocked MCP server dan mocked agent runtime untuk mensimulasikan perilaku tool tanpa panggilan jaringan yang sebenarnya.

\subsection{Refleksi}

Pengujian keamanan (pencegahan SQL injection) menunjukkan bahwa validasi input harus diuji seteliti logika bisnis; kegagalan validasi dapat menjadi kerentanan yang tidak terdeteksi oleh pengujian fungsional biasa. Mencapai cakupan 100\% pada tool yang memanggil Google Drive API atau database membutuhkan desain mock yang jujur: yang diuji harus logika tool, bukan perilaku mock itu sendiri.

Integration test terhadap database sungguhan menemukan masalah yang tidak tertangkap mock, misalnya kegagalan insert karena nilai NULL dan ketidakcocokan tipe data antara model dan skema database. Dari pengalaman itu, saya sekarang selalu melengkapi unit test dengan minimal satu integration test untuk modul yang menyentuh database.
